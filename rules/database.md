# Database Rules

## No ORM — raw SQL only

- **No SQLAlchemy ORM, no declarative models, no `select()`/`Session.query()` query
  building anywhere in application code.** All queries are raw SQL strings executed via
  `asyncpg`, parameterized with `$1, $2, ...` positional placeholders (asyncpg's native
  style — never string-interpolate values into SQL).
- `SQLAlchemy` remains installed as a dependency **only** because Alembic uses it
  internally to run migrations — it is never imported in `routers/` or `services/`.
- `database/models.py` holds plain `@dataclass` type definitions (one per table) for
  type hints and IDE support only — they are not database-mapped, have no ORM
  behavior, and rows are built into them manually after a raw query (`Account(**row)`
  after `dict(row)` from an asyncpg `Record`, or explicit field-by-field construction).

## Connection & Pool

- One `asyncpg.Pool` created at app startup (FastAPI lifespan in `main.py`), closed at
  shutdown. `database/session.py` exposes `get_db()`, a dependency that acquires a
  connection from the pool for the request and yields it as an `asyncpg.Connection`.
- Writes that touch more than one statement (e.g. create profile + default account)
  run inside an explicit transaction: `async with conn.transaction(): ...`.
- Never manage the pool or acquire connections manually in routers — always through
  `get_db()` dependency injection.

## Query Style

```python
# services/account_service.py
async def get_accounts(profile_id: int, conn: asyncpg.Connection) -> list[Account]:
    rows = await conn.fetch(
        "SELECT * FROM accounts WHERE profile_id = $1 AND is_active ORDER BY sort_order",
        profile_id,
    )
    return [Account(**dict(row)) for row in rows]
```

- `conn.fetch(...)` for multiple rows, `conn.fetchrow(...)` for zero-or-one,
  `conn.fetchval(...)` for a single scalar, `conn.execute(...)` for writes with no
  return value.
- Every query is parameterized — `$1`, `$2`, positionally, passed as separate
  arguments to `fetch`/`execute`. **Never** f-string or `.format()` a value into SQL.
  Table/column names (never user input) may be composed via `str` when genuinely
  dynamic (e.g. a `Literal`-validated sort column); values never are.
- Money math stays exact: `Numeric(12,2)` columns in Postgres map to Python
  `Decimal` — asyncpg returns them as `Decimal` automatically; never cast to `float`
  for anything that gets summed, compared, or stored back.

## Migrations

- Alembic remains the migration **runner** (versioning, `alembic upgrade head`,
  `alembic_version` tracking) — but migrations are **hand-written raw SQL**, not
  autogenerated from ORM models (there are none to diff against).
- A migration file is a normal Alembic revision whose `upgrade()`/`downgrade()` call
  `op.execute(...)` with the literal SQL. Write the DDL by hand; review it like any
  other code.
- **One statement per `op.execute()` call — never a semicolon-joined multi-statement
  string.** Alembic's async runner goes through SQLAlchemy's asyncpg dialect, which
  always uses the prepared-statement protocol; asyncpg allows exactly one command per
  prepared statement and raises "cannot insert multiple commands in a prepared
  statement" otherwise. Keep migrations as a list of individual SQL strings executed
  in a loop (see `0001_initial_schema.py` for the pattern), not one big triple-quoted
  block.
- Every schema change ships as a new revision. Never edit an applied migration.
- Generate a new empty revision to fill in by hand: `alembic revision -m "description"`
  (note: **no** `--autogenerate` — there's no ORM metadata to diff against).

## Naming Conventions

- Table names: lowercase plural (`users`, `transactions`, `categories`)
- Column names: lowercase snake_case (`hashed_password`, `transaction_type`)
- Foreign key columns: `{table}_id` (`profile_id`, `category_id`)
- Indexes named explicitly: `ix_{table}_{columns}`; unique constraints: `uq_{table}_{columns}`

## Type Dataclasses (`database/models.py`)

- One `@dataclass` per table, fields matching columns exactly (name and type).
- No relationships, no lazy loading, no session state — a dataclass instance is just
  a typed bag of the columns for one row. Related data (e.g. a transaction's category
  name) comes from an explicit `JOIN` in the query, not from touching an attribute.
