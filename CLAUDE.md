# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Privacy-first personal finance app, self-hosted on localhost. One login per person, 1–3
sealed single-currency **country profiles** per user (USA/India/Canada — never merged,
no currency conversion). Capture via natural-language quick-add or document scan
(receipt/bill/statement, dedup-safe); advises via monthly/annual breakdowns, recurring-bill
detection, cash-flow forecast, and "safe to spend."

**Read before non-trivial work:** `docs/plan.md` (roadmap + definition of done) and
**`docs/backlog.md`** — the ticket file. All implementation work comes from there: pick
the lowest open ticket whose dependencies are done, stay inside its scope, never invent
work. Reference specs: `docs/architecture-and-goals.md` (system + data model + AI
allocation — some sections are older planning notes for features already shipped, cross-check
against actual code when in doubt), `docs/design-system.md` (3-color UI rules + page map).

## Commands

**Frontend** (from `frontend/`):
- `npm run dev` — Vite dev server (also runs inside Docker via `docker compose up`)
- `npm run build` — `tsc && vite build`
- `npm run typecheck` — `tsc --noEmit` only
- `npm run lint` / `npm run lint:fix` — ESLint
- `npm run format` / `npm run format:fix` — Prettier, `src/**/*.{ts,tsx,css}`
- `npm run test` — Playwright e2e suite (`frontend/e2e/*.spec.ts`); `npm run test:headed` to watch it run
- Single test file: `npx playwright test e2e/auth-flow.spec.ts`; single test by name: `npx playwright test -g "test name"`

**Backend** (from `backend/`):
- `uvicorn main:app --reload` — dev server
- `ruff check .` / `ruff check --fix .` — lint
- `ruff format .` — format
- `alembic upgrade head` — apply migrations
- `alembic revision -m "description"` — new migration (**no** `--autogenerate` — there's no ORM metadata to diff against; fill in the raw SQL by hand)
- No pytest files anywhere by convention — verify backend logic via curl + hand-computed
  fixtures against the running server, not automated test files. (`pyproject.toml` has an
  unused `[tool.pytest.ini_options]` section — leftover, not a real test suite.)

**Everything**: `docker compose up -d` (Postgres + backend + frontend). Frontend on
`:3000`, backend + `/docs` (OpenAPI) on `:8080`.

**Data safety** (`scripts/`): `backup.ps1` writes a verified `pg_dump -Fc` with count-based
retention; `restore.ps1` restores one (newest by default) into a dropped-and-recreated
database and verifies row counts afterwards. **Rehearse before trusting it** —
`restore.ps1 -TargetDb restore_test -Confirm` proves a dump is restorable without
touching live data. Once real data exists, take a backup immediately before any
`alembic upgrade`: the restore, not the downgrade, is the rollback path.

**Required after every change**: run the relevant lint/format/typecheck commands above,
verify live (curl/fixtures for backend, Playwright against both viewports for any UI
change), then self-review the diff — run the `/code-review` skill (`.claude/skills/code-review/`)
before committing anything non-trivial.

### Known dev-environment gotcha
On Windows + Docker Desktop, the `frontend` container's bind-mounted file watcher can
silently miss host-side edits — Vite keeps serving a stale transform of a changed file
instead of picking it up via HMR (confirmed by diffing the served module against the
on-disk file). If an edit doesn't seem to take effect in the running app, `docker compose
restart frontend` before assuming the change itself is wrong.

## Architecture

### Backend — thin routers, raw SQL, no ORM
`backend/`: `core/` (config, security, logging, rate-limit middleware) · `database/`
(asyncpg session/pool, `models.py` — plain `@dataclass` row types, Alembic migrations) ·
`routers/` (one file per resource, thin: Pydantic validation → service call → response) ·
`services/` (all business logic, including `ai/` for the Gemini wrapper and `ingest/` for
document extraction). One `asyncpg.Pool` created in `main.py`'s lifespan; routers get a
connection only via the `get_db()` dependency, never manually.

**No SQLAlchemy ORM anywhere in application code** — all queries are raw parameterized
SQL (`$1, $2, ...`) via `asyncpg`. SQLAlchemy is installed only because Alembic uses it
internally to run migrations. Migrations are hand-written SQL in `op.execute()` calls, one
statement per call (asyncpg's prepared-statement protocol forbids multi-statement
strings) — never autogenerated. Money is `Numeric(12,2)` in Postgres / `Decimal` in
Python, never cast to `float`. Full contract: `rules/database.md`.

Auth is JWT (`PyJWT`, HS256) with `bcrypt` password hashing. Every financial route depends
on both `get_current_user` and `get_current_profile` (validates the requested country
profile belongs to the authenticated user). Full contract: `rules/backend.md`.

### AI tiers (strict opt-in boundary)
1. Rules/statistics + local document extraction (pdfplumber text-layer + Tesseract OCR) —
   always on, zero network calls, the default.
2. Local LLM (Ollama) — considered and deliberately dropped; don't reintroduce without a
   fresh decision (see `services/ingest/document_extract.py`'s header comment).
3. Gemini (cloud, free tier) — the **only** external call the app ever makes, and only for
   users who've flipped their `ai_cloud_enabled` toggle on (off by default). Every call
   site must check that toggle before calling `services/ai/gemini.py`'s `call_gemini()`.

### Frontend — desktop/mobile split, Zustand-only state
`frontend/src/`: `desktop/` and `mobile/` are **separate UI trees** with separate page
maps (desktop = Home/Activity/Recurring/Insights/Manage; mobile = Home/Activity/Capture,
settings behind the avatar menu) — feature parity between them is a non-goal, and
cross-imports between the two trees are banned. Both import freely from `shared/`
(hooks, api client, types, formatting) and `store/` (Zustand slices) — anything without
JSX lives in one of those two, never inside `desktop/`/`mobile/`. Every component is
`Name.tsx` + `Name.module.css`; no Tailwind, no inline styles.

**One deliberate exception — `shared/pages/` may hold JSX** (added by ZC, 2026-08-08):
`Login` and `Register` only. Auth is not device-role-differentiated — a login form is a
login form — and the two copies had drifted to 248-vs-247 and 349-vs-339 near-identical
lines. They are now one component each, with the small chrome differences (card border,
padding, heading size) expressed responsively at the 768px boundary that already splits
the two trees. **This exception does not generalise**: everything else with JSX still
belongs to exactly one tree. The measured reason is in `backlog.md` ZA — `mobile/` is
2,709 LOC to `desktop/`'s 8,107 across half the pages, so the trees are genuinely
different apps, not copies, and merging further would force desktop-only pages onto a
390px screen.

**State is Zustand-only** — no React Query, no Context for global state. One bound store
(`store/useBoundStore.ts`) combines every domain slice via the `namespaceSlice` helper
(`store/namespaceSlice.ts`), which nests both state *and* actions under one key (e.g.
everything auth-related lives at `s.auth.*`, called as `s.auth.login(...)`). Components
only ever import `useBoundStore`, never a slice file directly. The load-bearing gotcha:
inside a slice creator, `get()` returns only that namespace's *state*, not its actions —
calling a sibling action via `get().otherAction()` is `undefined()` and throws silently;
call it as a local closure over `set` instead. Full contract, including the
useState-vs-Zustand threshold ("2+ pieces of state → Zustand", even for transient form
state) and the slice-creation recipe: `rules/zustand.md`.

Colors come from exactly one place — `theme.tsx` (Radix `<Theme accentColor="orange"
grayColor="slate">`) + `styles/design-tokens.css`. No hex/rgb/hsl in any `.module.css`.
Three-color system: slate for backgrounds/text ("paper"/"ink"), orange for actions only
("accent," max ~3 visible per screen), green/red on transaction amounts only — never on
containers or badges. Full contract: `rules/ui-ux.md` and `docs/design-system.md`.

### Country-profile data model
One `users` row = one login = 1–3 `profiles` rows (at most one per country: US/IN/CA),
each a sealed single-currency world — accounts, categories, transactions, bills, goals,
budgets, merchants, documents all key off `profile_id`, never blended or converted across
profiles. The active profile is chosen client-side and sent as a header on every
financial request; switching profiles is a full data swap, not a merge.
